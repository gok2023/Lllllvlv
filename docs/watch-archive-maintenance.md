# 观影档案维护验收

## 资产与操作

当前资产包括按服务和用户隔离的快照、旧档案的独立媒体库修正文件、用户导出的版本化 JSON、手动指定的 Playback Reporting 路径。当前快照内有有效媒体库修正、媒体目录、逐次播放、补录及固定基线、确认、待处理候选、已应用操作和撤销 ID、人工身份关联、设置、媒体库目录及同步游标。路径文件不随观影档案导出；迁移设备时须重新核对本机数据库路径。

版本 3 导出包含快照和修正；导入兼容版本 1、2、3，以及本程序生成的原始快照 `.backup` 文件。预览显示各类数量及同 ID 不同内容的冲突数。预览后若文件、当前档案或服务用户改变，确认导入会拒绝，须重新选择和预览。无冲突合并按稳定 ID 去重，保留两边独有资产；冲突时拒绝合并。替换采用导入档案，写入前备份当前快照及修正，写入失败时尝试回滚。主快照、每日自动备份和导入前备份通过同目录临时文件完成后重命名。磁盘故障和断电仍需独立副本。人工关联只在用户确认两项同源同类型作品后保存；标题相同不是自动关联证据。具体持久化契约见 [观影统计](watch-statistics.md)。

默认档案目录是 `%APPDATA%\Freebo\watch-statistics\`；若在「设置 → 常规」选择了自定义数据目录，则到该数据目录下的 `watch-statistics\`。当前快照为 `<serverId>-<normalizedUserId>.json`，导入前自动备份是同名文件后接时间戳和 UUID、以 `.backup` 结尾，日常自动备份以 `.auto.backup` 结尾。导入前备份包含写入前的快照与修正；日常备份只在相关写入流程触发，不保证首次启动或升级前自动创建。最多保留最近五份导入前备份和五份日常备份；重要版本应另行导出并保存。

操作顺序：先用「导出数据」保存当前用户档案；在目标服务网页登录正确用户；用「导入数据」选择版本化 `.json` 或上述原始 `.backup`，检查预览的数量、时间范围、冲突和媒体库修正警告；按需要选择合并或替换；完成后核对确认、补录、修正和统计范围，再执行完整同步。要回退一次导入，在同一服务和用户下重新选择那次导入前生成的 `.backup`，预览后选择「导入并替换」，无需编辑 JSON。跨设备媒体库 ID 可能不同，修正是否仍指向目标媒体库须人工核对。真实用户档案、安装版和跨设备操作均未由本报告自动执行。

**当前快照本身损坏时的恢复。** 导入预览也要读取目标档案，损坏的目标会阻止直接替换。先完全退出应用并复制整个 `watch-statistics` 目录，保留原始字节。在隔离的数据目录或副本中，将目标服务用户的主快照及对应旧 `.corrections.json` 移至另一个保留目录，再预览带校验的导出或可读的 `.backup`。核对确认、实播、补录和修正后再决定正式恢复。若最近一份备份也损坏，使用上一份可读副本。未导出且上游已过期的本地历史无法从一次完整同步重建。

**新库先出现临时文件名、后补外部标识的两种结果。** 旧档案带一条 3,600 秒基线和首次确认，新库同片最初无 TMDb。新条目没有已观看状态时，补齐唯一 TMDb 后旧确认自动归入当前作品，仍只有 3,600 秒估算。若新条目此前也独立形成了首次确认与估算，系统保留两条基线并提示一个冲突，重复核对不会继续增加。此时汇总包含 7,200 秒，须人工判断两项是否代表同一次观看。既有双基线不能在关联对话框直接强制合并。处理前应导出双方档案，有可信历史副本时先在隔离目录验证恢复结果。

## 大库同步测量

Windows、Node 24.17，使用临时目录和实际 Store。本机内存响应模拟一个库，每部电影有唯一 TMDb、一个 600 秒事件、Played 为假。全量每页 500 项，增量回看最近 168 条。以下为同一台机器的墙钟样本，包含解析、身份核对及本地文件处理。远程查询、Electron IPC、网络带宽和插件锁等待由实机决定。

| 6,000 部电影 / 6,000 个事件 | 修改前（66e2b0e） | 修改后 | 上游请求 |
| --- | ---: | ---: | --- |
| 无变化增量，连续两轮 | 477 / 444 ms，每轮写 4,479,113 字节 | 100 / 93 ms，两轮均零写入 | 各 1 次 Views、1 次插件查询 |
